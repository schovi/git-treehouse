# Main view

_Behavior spec. Index: [docs/README.md](../README.md) · Code: [docs/architecture.md](../architecture.md)._

## Table

Borderless table. By default it shows one row per worktree unless `show_branches` is enabled. Pressing `b` also shows local branches that are not checked out by any worktree. Columns left to right:

| Column | Content |
|---|---|
| name | Row-type glyph plus display name, with optional lifecycle suffix, e.g. `⌂ main`, `⊡ feature/work`, `⊡ cd5e190 detached`, `⊡ stale/abandoned ×`, or `⎇ feature/local-only` |
| status | Working-tree state, compact (see [Status column](./columns-and-data.md)); `-` for branch-only rows |
| remote | Ahead/behind vs upstream, e.g. `↑2 ↓1`; `✓` when synced; `gone` when upstream was deleted; `-` when no upstream |
| main± | Ahead/behind vs the local main branch, e.g. `↑5 ↓12`; blank only for rows already on the main branch |
| commit | Short SHA + truncated subject line |
| age | Relative last-commit time (`3h`, `2d`, `5w`) |
| PR | PR number + state + CI (see [GitHub data (PR column)](./columns-and-data.md)), rendered as a clickable OSC 8 hyperlink |
| size | Git-aware worktree size, computed lazily from tracked and unignored untracked files (see [Data loading model](./columns-and-data.md)) |

Column sizing: name and commit are elastic. The renderer drops or shrinks columns in this order: size, shrink commit to its short SHA, PR, age, shrink name, main±, remote, then commit. Below 40 columns, only name and status remain in the compact layout.

When rows exceed the available table height, a two-column scrollbar gutter appears at the right edge of the table. It includes up/down arrows, a proportional thumb, and a track; the table content narrows to make room.

The header includes the root repository branch, e.g. `root: codex/list-rendering-polish`, because the root repository can be checked out to a non-main branch.

## Row lifecycle and type icons

Row-type icons live inside the name column before the displayed name. Lifecycle icons for exceptional worktree states are suffixes in the name column. Selection and current-worktree state are rendered with text style, not marker glyphs.

Lifecycle suffixes:

| Glyph | Meaning |
|---|---|
| `!` | Locked worktree |
| `×` | Prunable worktree, directory missing on disk |

Type icons:

| Glyph | Meaning |
|---|---|
| `⌂` | Root repository, the primary checkout that owns the worktree set |
| `⊡` | Checked-out worktree |
| `⎇` | Local branch without a worktree |

The name column starts with exactly one row-type glyph and one space before the displayed name. The header label `name` aligns with the displayed name, leaving the row-type glyph area untitled. Locked and prunable worktrees append one lifecycle glyph after the displayed name. Detached worktrees still show `<sha> detached`, prefixed by the worktree type icon.

## Selection and current worktree

- The current worktree, where `git-treehouse` was started, uses bold row text.
- The selected row uses a full-row background only. Selection does not add bold text or a row marker.
- If the current row is selected, both styles apply: full-row background plus bold row text.

## Detail panel, local hints, and status bar

Below the table:

- **Worktrees footer:** list-local hints live in the bottom border of the Worktrees panel. The left side contains collection actions. In normal mode this shows `n new worktree` on the left and `h root · a active · Tab filter: <state> · s search · b branches` on the right. With branches visible it shows `b hide branches`. With an active filter, it also shows `Esc clear filter`. A committed search shows `search: <text>` on the left; while editing, it shows `search <text>▌` and the right side shows `Esc clear · Tab filter: <state> · b branches`. With the scrollbar gutter visible, normal-mode hints prioritize `Tab filter: <state> · s search · start/total`; narrow panels drop whole trailing hints before truncating. An empty result names its active filter and search, with the keys needed to clear them.
- **Detail panel:** full info for the selected row. Worktree rows show branch name, explicit `HEAD`, root/current state, a path relative to the active worktree (or root when there is no active worktree), full status counts, Git-aware and full size when loaded, lifecycle/delete notes. A clean, removable worktree whose branch is merged to main or whose PR is merged/closed shows a green `finished: … — safe to remove (d)` hint; it calls out a deleted upstream when present. It never appears for root, active, dirty, detached, locked, prunable, or still-loading rows. It falls back to the absolute path only when no relative path can be calculated; `y` always copies the absolute path. Neither worktree rows nor branch-only rows show the main-branch comparison, commit subject, remote/upstream state, or PR in the Detail panel, because the paired frames already cover them (the commit as the Git context HEAD node, the main comparison as its parent header row, the remote sync as its remote header row, and the PR as the PR review frame). Branch-only rows therefore show only branch name, explicit `HEAD`, `Path: not checked out`, `Status: no worktree`, `Dirty: -`, `Size: -`, and the checkout action, mirroring the worktree panel's shape. Root/current context appears next to the Details title, for example `Details · Current root repository`; branch-only rows use `Details · Local branch`. Selected-row actions live in the bottom border: worktrees show `↵ go · o editor · d delete · y abs path · p PR`; branch-only rows show `↵ create+go · c checkout root · d delete · y name · p PR`.
- **Context frames:** optional bordered blocks below the Detail panel that drill into the selected row. They reuse the same section-box renderer as the Details and Worktrees panels and are state-driven, so an irrelevant frame is not rendered. The table auto-shrinks to make room, so frames never push content past the terminal height. The space reserved for the detail region is the tallest any row in the list needs, not the selected row's own height, so moving the selection never resizes the table (a row with a shorter detail region leaves blank lines below its frames instead). **Layout:** the frames form two columns. The left column stacks the Details box, then Changes, then PR review; the right column is the Git context frame, which grows to match the left column's full combined height (bottom borders aligned). On a panel at least 104 columns wide the two columns render side by side (each roughly half width with a one-column gutter); below that threshold everything stacks full width in order Details, Changes, PR review, Git context.
  - **PR review frame:** shown for a row whose pull request (open or merged) has loaded review detail (GitHub lookup enabled), when the panel is at least 50 columns wide. Title `PR review · #<n>`. Lines, in order: `state`, `checks` (passed/failed/running/skipped roll-up), then `review` (`approved` / `changes requested by N` / `review required` / `no review yet`). The `state` line reads `open`/`closed`/`merged` (a merged PR is prefixed with a purple `⎇` git glyph matching GitHub's merged badge), appends `· draft` only when the PR is a draft, and ends with GitHub's real merge-state status as a colored third token so it matches the web UI: `ready to merge` (green; clean + approved + no blockers), `blocked by merge requirements`, `merge conflicts`, `behind base branch`, or `checks not passing` (red/amber); the token is dropped when the state is draft-only or unknown. Failing (`✗`) and running (`●`) checks are listed individually under the checks line (capped, `+N more checks`), each an OSC 8 hyperlink to the check's detail page; passed and skipped checks stay in the roll-up. Change-request reviews (top-level `CHANGES_REQUESTED` summaries) are listed under the review line as one-line previews `@author <first line>` (capped), each linking to the pull request. Review detail is fetched lazily for the selected row via `gh pr view --json`; change-request previews link to the PR conversation because gh exposes no per-review permalink. While the lookup is in flight for an open PR, the frame stays visible with a `loading review…` placeholder (titled with the PR number) so the layout does not jump when it arrives; a finished attempt that failed or found nothing (including when `gh` is missing) leaves the frame hidden rather than stuck loading.
  - **Git context frame:** shown for a non-main worktree row or a branch-only row once its local graph has loaded, when its box is at least 50 columns wide (so when paired side by side with Details it needs a panel of at least ~104 columns; stacked, just 50). Title `Git context`. For a branch-only row (no checkout to log from) the branch tip ref stands in for HEAD throughout, and the graph is fetched lazily when that branch is selected (not eagerly for every local branch). A two-row labeled header sits above the graph, formatted as an aligned label column plus value so it reads as a small key/value block, visually distinct from the flush-left `●` commit rows (a blank line separates the two). The first row is labeled with the parent branch name (e.g. `master`) and its value shows colored ahead/behind arrows matching the table's `main±` column (`↑<ahead>` amber, `↓<behind>` red) plus the current branch as `→ <current>` (e.g. `master  ↑2 ↓5 → feature/login`), or `in sync · <sha>` when there is no divergence. The second row is labeled with the short remote name (e.g. `origin`, or `remote` when there is no upstream) and its value mirrors the table's `remote` column: a green `✓ synced`, the same colored `↑`/`↓` arrows when ahead/behind, `gone` when the upstream was deleted, or `no upstream` for a local-only branch. This remote row is the only place the row's remote sync state is shown; the Detail panel no longer repeats it. Below the header, an ASCII graph draws the history. When the worktree has actually diverged (it is behind main on some commits), it uses two rails: the parent (main) trunk runs down the left as dim `●` nodes (the commits the worktree is behind on, newest first, capped with `┆ +N more on main`); the worktree's own commits sit on a rail to the right as bright `●` nodes (`│ ●`, newest first, the topmost tagged `← HEAD`, capped with `│ ┆ +N more ahead`); a `├─┘` fold returns that rail into the trunk just above the fork point. When the worktree is only ahead of main (behind 0, a clean fast-forward), there is no divergence to draw, so the side rail and fold are dropped and the commits render as a single straight column ending on the fork point. The fork point renders as a real commit `● <sha> <subject> ← fork point` (the merge-base both sides share). When the worktree has no commits of its own, HEAD coincides with the fork point and the node is tagged `← HEAD` instead. The upstream is woven into the same branch line as real nodes rather than a floating marker: commits the remote has that HEAD lacks (a pull would bring them in) render as `◆` nodes in the remote (label) color above HEAD, the newest tagged with the remote name (e.g. `← origin`), and fold back into HEAD; when HEAD is ahead of the remote (unpushed commits), the commit the remote points to gets a `← <remote>` ref label so everything above it reads as unpushed. To keep a small divergence from collapsing to one or two lines, shared ancestor commits below the fork point pad the graph up to a minimum of five commit rows. When the frame renders side by side with the left column, it grows further to match that column's combined height (Details + Changes + PR review): it shows more shared ancestors (fetched deeper for this reason) and, only if it runs out of real history, blank lines, so the outer bottom borders align rather than leaving the shorter side floating. Rows are not interleaved by commit date (main above, our branch below) so "parent ahead, we branched aside" reads at a glance. Commit data comes from local `git log` calls per row (`<main>..<ref>`, `<ref>..<main>`, `<ref>..<upstream>` for the upstream commits, and `git merge-base` plus a deeper log from it for the fork point and its ancestors), where `<ref>` is `HEAD` run from the worktree path for a worktree row, or `refs/heads/<branch>` (with `<branch>@{u}` for the upstream) run from the repo root for a branch-only row; totals come from the row's main-branch ahead/behind.
  - **Changes frame:** shown for every worktree row (it pairs beneath Details in the left column) when the box is at least 50 columns wide; a clean worktree renders the frame with a single `no changes` line rather than collapsing. Title `Changes`. A summary header (`N files · +A/-D · S staged M modified U untracked`) sits above one line per changed file: a staged marker (`*`), a status glyph (`A` added / `M` modified / `D` deleted / `R` renamed / `?` untracked, color-coded), the left-truncated path (filename kept), and right-aligned `+adds`/`-dels`. Untracked files show `new` instead of stats. Files are ordered staged, then modified, then untracked, each group by descending churn. The list is capped (8 rows) with a `+N more files` line so the frame height stays bounded. Line stats come from `git diff --numstat HEAD`; files without a numstat entry (binary, untracked) omit counts.
- **Status bar:** transient progress and flash messages only. The app frame title starts with `Git treehouse · <repo>`. The top controls show refresh age, help, and quit. Table-scoped refresh feedback lives in the Worktrees title instead of the status bar.
- **Help overlay:** groups shortcuts by context (`Global`, `Worktree List`, `Worktree Detail`) and groups visual legends (`Row Icons`, `Git Status`, `Pull Requests`). Category headers are bold white. The row lifecycle and PR legends live here instead of the status bar.
- `g/G` remains available and documented in help, but is not shown in the main view.
